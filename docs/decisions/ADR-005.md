# ADR-005: Generations for manual requeue and fencing

- **Context:** ADR-004 resets attempts to 0 when a DEAD job is requeued. After a requeue, attempt numbers repeat, so `(job_id, attempt)` no longer identifies one run. That breaks two things: handlers that detect repeats by `(job_id, attempt)` (Section 1.3), and fencing, which compares the attempt captured at claim time (Section 4, G5).
- **Decision:** Each job has a `generation`, starting at 0 and increased by one on every manual requeue. A run is identified by `(job_id, generation, attempt)`.
  - Handlers receive the generation with the job ID and attempt number, and use all three to detect repeats.
  - Every fenced worker write also checks `generation = :generation_at_claim`, alongside `locked_by` and `attempts`. This includes heartbeat renewal.
  - A requeue writes one `job_attempts` row with `generation` set to the new generation, `attempt = 0`, `outcome = 'MANUAL_REQUEUE'`, `manual_requeue = true` and no worker. The job gets `status = 'PENDING'`, `attempts = 0`, `run_at = now()`, a cleared lease, and keeps `last_error`.
- **Reason:** Without the generation check, a worker frozen since before a requeue could wake up holding attempt 3 just as the new generation reaches attempt 3, and its fenced write would match. Counting generations keeps ADR-004's reset while making every run unique.
- **Consequence:** Worker claim, heartbeat, complete and fail queries carry one more fencing condition. Each requeue's history row marks where a new generation starts, so the history of a job reads as one block of attempts per generation.
