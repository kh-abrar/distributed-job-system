# ADR-006: Answers to the open questions, and the API path

The spec (Section 11) left five questions open. Building the system settled three
of them, and the Phase 5 experiments answered the other two with measurements.
This ADR also records one deliberate difference from Section 3.

## Q1: How a worker backs off when it loses its database connection

- **Decision:** The same exponential backoff with jitter as job retries: 2 s doubling up to 60 s, half of it random. A failed claim is retried after that delay, and the count resets on the next successful claim (`WorkerRuntime`). A failed heartbeat is only logged; if the database stays unreachable the lease runs out and the job is recovered, which the failure model (Section 7) already expects.
- **Reason:** One retry rule is easier to reason about than two. Jitter keeps a fleet of workers that lost the database at the same moment from all reconnecting at the same moment.
- **Consequence:** After an outage, a worker can take up to 60 s to start claiming again.

## Q2: Do the reaper and the claim query honour run_at the same way?

- **Decision:** Yes. The claim only takes jobs with `run_at <= now()`. A failed attempt sets `run_at = now() + backoff`. The reaper sets `run_at = now()`, with no backoff, so a recovered job is claimable at once. Every one of these uses PostgreSQL's `now()` (Assumption 3).
- **Reason:** A job lost to a crashed worker didn't fail on its own, so delaying it would only stretch recovery past G3's "lease duration + reaper interval" bound.
- **Consequence:** Tested in `JobStoreTest`: a job waiting for its backoff isn't claimed, and a reaped job is claimed immediately.

## Q3: How much job_attempts history to keep

- **Decision: keep it all for now.** Nothing is pruned or archived. Each run adds one row; a job uses at most `max_attempts` rows per generation, plus one per manual requeue.
- **Measured (Phase 5):** about 200-230 bytes per row including indexes, so a million runs is about 200 MB. At this project's scale, retention isn't worth the complexity yet. Revisit if the table reaches tens of millions of rows; a time-based partition or an archive of attempts older than some months would then be the natural next step.

## Q4: Size limits for result and last_error

- **Decision for errors:** `last_error` and `job_attempts.error` are capped at 2,000 characters, cut without splitting a character (`JobStore`).
- **Still open for results:** No limit. The three built-in handlers return a few dozen bytes, and arbitrary user code is out of scope (Section 1.5). Add a limit if a handler that returns large results is ever added.

## Q5: When polling becomes the bottleneck, and whether to bring in Redis Streams

- **Measured (Phase 5): not yet.** At 307 jobs/s, PostgreSQL spent about 10% of one CPU on worker statements; at 3,477 jobs/s (4 workers, near no-op jobs), about 1.6 of 12 CPUs. The average claim took twice as long at the higher rate (0.18 ms to 0.39 ms) as workers contended for rows, but the database never saturated. The cost of idle polling against an empty queue wasn't measured.
- **What did limit scale first:** database connections. Each worker's pool defaulted to 10 connections (HikariCP's default), so a default PostgreSQL (100 connections) ran out at about 9 workers.
- **Done since:** the worker now sizes its pool to `worker.threads + 3`: one connection per handler thread, plus the poll loop, the heartbeat and the reaper (`WorkerPoolSizer`). That's 7 with the default 4 threads, so about 12 workers fit. A back-to-back A/B test showed no throughput cost: a median of 3,519 jobs/s with 7 connections against 3,464 with 10. An explicit `spring.datasource.hikari.maximum-pool-size` still overrides it.
- **Decision:** no Redis Streams for now. ADR-002's condition for bringing it in, polling becoming the bottleneck, hasn't been met at any rate measured. Details: [docs/05-experiments.md](../05-experiments.md).

## The API is served under /api

- **Decision:** All endpoints from Section 3 live under an `/api` prefix: `POST /api/jobs`, `GET /api/jobs/{id}`, and so on. The paths after the prefix match Section 3 exactly.
- **Reason:** The API was built under `/api` from the start, and the tests, README and Docker setup all use it. The prefix also leaves the root free for endpoints that aren't part of the job API, such as health checks.
- **Consequence:** Section 3's table should be read with the `/api` prefix. The spec text itself is unchanged, so this ADR is where the difference is recorded.
